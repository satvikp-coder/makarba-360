# Privacy, ethics and threat model

Planning baseline: 2026-11-07. Proposed design; no participant collection or product implementation has occurred.

Real participant collection is blocked until institutional research approval and applicable-law review are recorded by the authorised institutional owner. This is a verification task, not a claim of legal compliance. Check India's applicable DPDP framework, commencement, institutional policies, participant ages, hosting/transfers and notice/withdrawal obligations using current official sources with institutional counsel. No child-participant workflow until specifically approved. No ordinary respondent names, phones or addresses are required.

Consent is voluntary and versioned: research recording/aggregate analysis, quotation, identifiable attribution, photo, audio/video and publication are distinct scopes. Refusal stops responses and GPS; retain only nonidentifying refusal tally if approved. Withdrawal uses an optional participant-held random receipt, not public search by name; lead verifies request privately. Partial withdrawal revokes only relevant scopes and invalidates derived publication.

| Threat | Control | Verification |
|---|---|---|
| Anonymous raw-data query | Public DB role has no private grants; allowlisted DTO | Negative API/DB tests |
| Cross-researcher IDOR | Ownership and assigned study checks on every operation | Substitute valid other-owner IDs |
| Role escalation/session theft | OIDC authorization-code with PKCE through backend; secure HttpOnly SameSite cookies; server sessions; MFA for lead/admin | Revoked session, wrong role, CSRF tests |
| CSRF/XSS/injection | CSRF token+origin checks for cookie writes; CSP, output escaping, prepared queries, no arbitrary HTML | Malicious fixture + cross-site requests |
| Lost offline device | Device lock/encryption, protected vault, unlock expiry, least local data | Loss/recovery drill; document residual risk |
| Dangerous upload | MIME sniffing, bounded size, quarantine scanner, decoder isolation, no active SVG/HTML | Polyglot/oversize/malware fixtures |
| Re-identification | Coarse approved cohorts, minimum n, complementary suppression, limited filters | Differencing and intersection tests |
| Public media location leak | Separate derivatives, EXIF removal, face/plate review | Decode metadata and visual review |
| Insider publishing | Independent approval, immutable audit, consent at current revision | Self-approval and stale-revision rejection |
| Backup/log leak | Encrypted backups, restricted keys; no payload/GPS in logs | Restore/access and redaction tests |

TLS everywhere; encrypted storage through selected provider with separately controlled keys; secrets in deployment vault, never Vite client env. Rate limits for login, sync, export and public queries; bounded expensive geospatial queries. Private responses `Cache-Control: no-store`, no service-worker caching. Sanitized request IDs and metrics only; no raw answer analytics SDK.

Provisional retention for approval: unsynced vault max 7 days with escalation (no automatic unacknowledged deletion); acknowledged local drafts purge within 24 hours; raw interview/GPS/consent 12 months after accepted final report, then approved purge or approved justified extension; public derivatives until licence/consent expiry; operational logs 90 days; encrypted backups rolling 35 days; minimal non-content audit 2 years. Institutional retention may override these before collection. Withdrawal removes public copies promptly, queues database/media purge, records tombstone and reapplies tombstones on restore; backups age out under approved policy. No silent deletion of unsynced work.

Incident response: contain exposure, disable affected publication/session, preserve minimal restricted evidence, assess with institutional lead, notify through verified obligations, rotate keys, restore safe snapshot and record corrective tests. No fabricated notification deadlines.

## Secrets and environments (issue #40)
`APP_ENV` (`local`, `staging`, `production`) is distinct from `NODE_ENV` and is mandatory when `NODE_ENV=production`; it is never guessed. At startup `@makarba/config` refuses: development placeholders and credentials outside local; a local database in staging/production; a remote database in local; non-TLS database URLs outside local; weak or short production session secrets (48+ characters); and `APP_ENV=local` under `NODE_ENV=production`. Errors name variables, never values; logs use `redactEnv`. Staging and production must hold different secrets: `sharedSecretNames` compares fingerprints in a deployment check (the vault itself is not in this repository). `scripts/scan_secrets.py` scans tracked files and, once web apps exist, their built bundles for server variable names, secret patterns and actual secret values; CI runs both. Limitations: no deployment vault or secret rotation is implemented here; the bundle scan has no bundle to scan until the first web app (it reports so rather than passing silently); scanning heuristics are not a guarantee.

## Database roles and grants (issue #36)
`db/bootstrap/001_roles_and_schemas.sql` (superuser, idempotent, no passwords) creates `makarba_migrator` (owns schemas, the only DDL role, used by the deploy job), `makarba_private_api` (DML on `private`, no DELETE; read `published`; append-only `audit`), `makarba_public_api` (SELECT on `published` only; no privilege of any kind on `private` or `audit`) and `makarba_worker` (reads `private`, writes `published`). All are `NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`; the deployment vault enables login per environment. Default privileges cover tables created by later migrations. Extensions are provisioned by the superuser. Pool limits: statement and idle-in-transaction timeouts and connection limits per role (public tightest). `db/tests/001_privileges.sql` proves, with synthetic tables, that the public role cannot read `private`/`audit`, write `published`, run DDL, create roles/extensions or alter itself; that the field role cannot publish, delete, alter schema or read audit; that the worker cannot write `private`; that no role can become another; and that the migrator has no superuser powers. CI applies the bootstrap to PostGIS twice (idempotence) and runs the tests. Limitations: row-level security is defense in depth and arrives with the tables (#22/#38); same-process public/private routing still shares one container (review finding F4); the superuser-driven test cannot exercise SET ROLE by a logged-in session, so role-switching is asserted from the catalog; the tests were run in CI, not on the author's machine (Docker unavailable locally).

## Identity and sessions (issue #32)
`@makarba/auth` + `apps/api/src/auth-routes.ts` implement ADR 006: OIDC authorization-code with PKCE (S256), per-login `state` and `nonce`, backend code exchange, ID-token verification (issuer, audience, expiry, signature via the provider JWKS, nonce) and **opaque server-side sessions**. Raw session and CSRF tokens exist only in the cookie/response; `private.sessions` (migration 0003) stores SHA-256 hashes, so a database read cannot replay a session. Cookies are `HttpOnly; SameSite=Lax` and `Secure` outside local. Sessions expire after 30 minutes idle and 12 hours absolute; logout, `revokeUser` and user deactivation take effect on the next request. Cookie-authenticated writes require `X-CSRF-Token` (constant-time compare). Pending logins are single-use and expire after 10 minutes; a callback whose state does not match the browser's login cookie is rejected before any token exchange. Sign-in is **deny by default**: only provisioned, active users in `private.users` may start a session (invitation workflow is #33). Error responses never include provider details.

MFA is a **provisional** policy: lead, reviewer and administrator sessions require an ID token whose `amr` shows a second factor (`mfaRequiredForRoles`). It is not final until the capability matrix (#6) is approved; role assignment itself arrives with #34, so until then every user has no roles and no MFA is demanded. Verified by: `pnpm --filter @makarba/auth test` (session lifecycle, PKCE, state/nonce/issuer/audience/expiry/signature failures against an in-process mock provider; PostgreSQL store tests run in CI), and `pnpm --filter @makarba/api test` (routes, CSRF, deny-by-default, MFA).

Limitations: no real identity provider is chosen or configured (no account purchased); behaviour against a real provider is unverified. Pending logins are held in process memory (single instance only). Expired-session purge needs a maintenance job (runtime roles cannot DELETE). Sessions are not yet bound to study/role grants (#34).

## Role and study authorization (issue #34)
`@makarba/authz` is the single, deny-by-default decision point. Policy is read from `docs/project/contracts/capability-matrix.json` (PROPOSED until #6 is approved); grants live in `private.user_roles` (migration 0004): a role scoped to one study, or system-wide for the administrator only, revocable and optionally expiring, with no self-grants. `Authorizer.can(principal, action, resource, context)` allows an action only if an active user holds an unexpired grant whose matrix access fits: `own` needs the record owner, `assigned` needs a grant for exactly that study, `grant` needs an explicit grant (restricted exports also need an approved purpose; break-glass needs a recorded reason and an expiry of at most 24 hours), `independent_reviewer` forbids approving your own work. Unknown actions, anonymous callers, inactive users, expired grants and other studies are denied. `canAssignRole` lets only user managers assign roles, never to themselves, never an unscoped researcher/lead/reviewer. In the database a trigger lets only the maintenance path create an `administrator` grant, so even a compromised API role cannot mint one. `requirePermission` (API) loads the principal per request, takes the resource from trusted server data and answers 403 without explaining why.

An exhaustive test enumerates every matrix action against every role (allowed with a matching grant; denied for another study, another owner, expired grant, inactive user, no grant) and found two matrix/engine mismatches during development (study-limited audit viewing by leads and system-wide break-glass), both fixed in the engine. The API refuses to start with `APP_ENV=production` while the matrix is not approved.

Limitations: no private research routes exist yet, so "every private route" is enforced by the middleware contract and its tests rather than by an inventory of routes (route inventory check arrives with #35/#38); role-hold of `reviewer` vs `lead` follows the proposed matrix; `study_area_id` is validated by the service, not a foreign key; the matrix is not approved, so production use is blocked by design. DB tests run in CI.

## Capability enforcement across API and UI (issue #35)
Private routes are declared only through `privateApi` (`apps/api/src/private-routes.ts`): each `PrivateRoute` must name a capability id from the matrix, and start-up/test validation rejects unknown ids, public ids and duplicates, so a typo fails closed. The router applies authentication, CSRF (for writes) and `requirePermission` to every route by construction; the resource (study, owner, author) comes from trusted server data. `GET /private/capabilities?studyAreaId=` returns the action ids the signed-in user may perform (advisory only) from the same engine, so the UI can show or hide controls consistently; tests prove the advertised capabilities equal the server's real outcomes and that a route called directly is still denied when the UI would have hidden it.

Limitations: the UI half of this issue (controls rendered from `/capabilities`) belongs to the field/admin front ends that do not exist yet; the capabilities are provisional until the matrix (#6) is approved; there are no research routes yet, so the per-route inventory covers only the framework and test routes.

## Security audit events and logs (issue #39)
`audit.security_events` (migration 0005) has no payload column: actor, capability id, allow/deny outcome, a fixed reason code, study/record identifiers, revision and a validated request id only. `@makarba/audit` validates every event against a closed allowlist (an extra field such as `payload`, `latitude` or `token`, or a value that is not a UUID, code or id pattern, is rejected) and the database re-checks the patterns, so free text cannot be stored. The table is append-only: runtime roles can only INSERT; UPDATE, DELETE and TRUNCATE are blocked by trigger even for the table owner and superuser. `requirePermission` records every decision; an *allowed* decision that cannot be audited is refused with a retryable 503 (fail closed), a denial stays a denial. `safeRequestLogger` logs method, route template, status, duration and request id only, so query strings (GPS), bodies (answers) and cookies (tokens) cannot enter logs.

Limitations: no audit reader exists yet (runtime roles cannot SELECT audit; a dedicated read role and the lead/administrator audit view arrive with the admin work, #95/#99); retention/purge of audit rows needs the approved retention policy (H3); only authorization decisions are wired so far, not future events such as publication or withdrawal; PostgreSQL tests run in CI.

## Researcher invitation, training and deactivation (issue #33)
Onboarding is invitation-only. A user manager creates an invitation (`AccountService.invite`): display label, a study-scoped role (never administrator or visitor) and a one-time token valid for 7 days, stored only as a SHA-256 hash (migration 0006); no e-mail or contact data is stored, and the token is handed over out of band. The invitee signs in with the identity provider; `/auth/login?invite=…` keeps the token server-side (never in the redirect URL or a cookie) and, only if the authenticated identity is unknown, redeems it in one transaction that creates the user and the study-scoped grant. Tokens are single use and refuse expired, revoked, unknown or replayed values and identities that already exist. Collection actions (`visit.start`, `interview.create`, `gps.capture`, `subject_location.link`, `media.submit`) additionally require a training record (`private.researcher_profiles`, recorded by someone else, never future-dated, never self-issued). Deactivation sets the account inactive and revokes every live session in one transaction; the authorizer and session validation both refuse inactive users, so a deactivated account can neither sign in nor act (sync will use the same checks, #57).

Verified by `packages/authz/src/accounts.test.ts` (PostgreSQL, CI) and `apps/api/src/auth-routes.test.ts`. Limitations: closure waits on #32 (real identity provider, matrix approval H1/H2); no administration UI yet (#95); invitation delivery is manual; the training *content* and who may certify it are an institutional decision (H3/H1); the offline sync check for deactivated users is exercised when sync exists (#57).

## Threat model and privacy-boundary tests (issue #41, independent part)

**Artifacts.** `docs/architecture/threat-model.json` (18 abuse cases, each with a status and a residual-risk statement), `apps/api/src/threat-model.test.ts` (21 tests against the real private-API construction, authorizer, session service and audit hook with in-memory stores and synthetic people), `apps/web/src/Xss.test.tsx` (2 tests), and `apps/api/src/safe-errors.ts`. A register test fails if an "automated" case has no test, if a test id is not registered, or if the register claims the capability matrix is approved while it is not.

**Cases and results.** Automated (12): unauthenticated/forged/tampered sessions (AC-01), CSRF on every write route (AC-03), cross-record and cross-study access and client-chosen study/owner (AC-04), identical responses for missing and forbidden records (AC-10), privilege escalation by role, inactive user, expired grant and untrained collector (AC-05), no self-publication and fail-closed on unknown authorship (AC-06), forbidden fields at any depth and spelling plus a read-only public API with no cookies (AC-07), restricted exports need a lead grant and an approved purpose (AC-08), malformed/oversized/hostile input and error bodies (AC-09), audit completeness and content-free events (AC-11), stored hostile text rendered only as text (AC-14), no-store caching (AC-16). Requires a live Developer A service (5): OIDC against the real provider (AC-02), uploads (AC-13, #60), consent bypass (AC-15, #37), raw interview and GPS endpoints (AC-17, #38), secrets in staging/production (AC-18, #40). Gap (1): rate limiting (AC-12).

**Defects found.**
1. Express's default error handler returns stack traces and local file paths whenever `NODE_ENV` is not `production` (reproduced with a malformed JSON body). `safe-errors.ts` supplies `notFound` and `safeErrors`; Developer A must mount them after all routes in the real server.
2. No rate limiting or lockout exists anywhere in `apps/api` (AC-12).
3. Requests without a session are rejected before the permission hook, so unauthenticated probing of private routes is not in the permission audit (AC-11).
4. A private router is only `no-store` if mounted behind `createApp` (AC-16).

**What these tests do not show.** The capability matrix is PROPOSED and unapproved (issue #6): the tests show that the code enforces the matrix it is given, not that the matrix is right. Consent enforcement is not testable server-side until consent records and raw-endpoint protection exist, so the headline criterion "valid authentication cannot bypass consent" is only partly evidenced here (publication review is; consent is not). The tests use in-memory session and audit stores, not PostgreSQL.

Remaining: (a) approval of the capability matrix (#6), a stakeholder decision; (b) re-running the register against Developer A's live endpoints (#38, #40) and consent records (#37). #92 (disclosure controls) has hard prerequisites #41 and #84. Today it is blocked by missing code (#84 aggregation, which itself waits for #37), not by missing test evidence: the disclosure rules (k-threshold, complementary suppression, constrained cohorts) already exist and are tested in `packages/analytics` for Developer A to reuse. The dependency on #41 is a legitimate final security gate for release, but it does not need to delay writing #92's code. Recommendation (not applied, because the allocation file is shared planning data): treat #41 as an integration/operational gate for #92's acceptance rather than a hard prerequisite for starting it, keeping the final security gate intact.
