# Visual design system

Planning baseline: 2026-11-07. Proposed design; no participant collection or product implementation has occurred.

Identity: a warm digital urban atlas combining geography, archival evidence and restrained photography. Avoid generic admin ornament and fabricated map art. Typography: locally hosted licensed Noto Sans for English plus Noto Sans Gujarati/Devanagari, with Noto Serif headings only if script coverage tested. Body 16px/1.5; captions 14px; headings fluid 28–48px. Dates/numbers align with tabular numerals. Spacing scale 4/8/12/16/24/32/48/64px, 8px panel radius, subtle single shadow, maximum prose width 70ch.

Tokens: background ivory #F6F2E9; primary text/deep teal #163D3B; accent terracotta #D27A55; sandstone #E6BC6C; lake #4C91A3. Use teal body text on ivory or sandstone only. Teal on terracotta/lake fails normal-text AA in the initial audit; use a tested darker foreground or reserve these accents for non-text decoration. Do not use light accent text on ivory for body copy. Contrast calculations below are generated using WCAG sRGB luminance; normal text ≥4.5:1, large text ≥3:1, focus/UI boundary ≥3:1. Dark focus outline with offset on light surfaces; light outline on teal. Marker icon+shape+label distinguishes category without color alone.

Breakpoints: <768 mobile, 768–1199 compact, ≥1200 desktop. Desktop header 64px, layers 256px, details 360px; map flexes. Compact uses collapsible drawers. Mobile header 56px, safe-area padding, 44px preferred touch targets, sheet peek 112px / half 50vh / full under header; drag gesture has equivalent buttons. No essential action depends on hover or dragging.

Controls: visible labels, input help and inline errors plus summary, real disabled reasons, save/sync statuses as text. Photo grids keep stable aspect ratio and date/credit; alt text describes evidence, never assumes historical cause. Charts use patterns/tooltips plus data tables. 160–220ms panel transitions, no compulsory map fly-through; reduced motion disables nonessential movement. Error red and success green are additional verified tokens to choose with AA contrast during design issue review; no status relies on color alone.

## Token specification and contrast evidence (issue #12)

Machine-readable tokens live in `packages/design-tokens` (`@makarba/design-tokens`); components must import them rather than hard-code colours. `assertTextPair()` throws for any foreground/background pair below WCAG 2.x AA (4.5:1 normal text, 3:1 large text and UI boundaries), so accent text that fails AA is rejected in code and tests.

Verified ratios (generated by the package tests, WCAG sRGB luminance):

| Pair | Use | Ratio |
|---|---|---|
| teal #163D3B on ivory #F6F2E9 | body text | 10.65 |
| teal on sandstone #E6BC6C | body text | 6.67 |
| ivory on teal | light text on dark | 10.65 |
| error #9B1C1C on ivory | error text | 7.29 |
| success #1E5E34 on ivory | success text | 6.95 |
| teal ring on ivory / sandstone ring on teal | focus outline | 10.65 / 6.67 |

Terracotta #D27A55 and lake #4C91A3 are decorative-only (`decorativeOnly`): tests assert that terracotta or lake as text on ivory, and teal text on either accent, are rejected. Error and success tokens above resolve the open item in this document.

Fonts: Noto Sans, Noto Sans Gujarati and Noto Sans Devanagari are published under the SIL Open Font Licence 1.1, which permits self-hosting and redistribution. Font files are not yet bundled; they will be added (locally hosted, no third-party font CDN) with the web app shell (#72). Gujarati/Devanagari rendering is to be checked by a human reader before localization is closed (#129).

Main navigation: Explore, Then & Now, Community Voices, Urban Insights, Research. Sources/credits and accessibility/language stay reachable from the footer on every page. Every route defines loading, empty and error states (empty research findings explain collection status; no-data is never shown as zero).

Public site is read-only: there is no Submit Survey entry, anonymous write journey, login or admin link in public navigation. URL state allows only listed privacy-safe parameters; `sanitizeQuery()` drops everything else and always drops keys containing `interview`, `participant`, `gps`, `lat`, `lng`, `coords`, `token`, `submit` or `survey`. Verified by tests (negative case: no survey/submit/login route or query key; forbidden params stripped).

Limitation: this is a design-time artifact; the actual router and shell are built in #72. Final requirement review (#7) is a soft input and not yet done.

## Desktop map-first layout (issue #15)

Layout at >=1200: header 64px, layers/search panel 256px, map flexes, details panel 360px expandable. At 768–1199 the layer panel and details panel become collapsible drawers (buttons with visible labels; Escape closes; focus returns to the opener).

| Concern | Specification |
|---|---|
| Focus order | skip link → header → search → layer toggles → place list/map → details panel; the map canvas is one tab stop with arrow-key pan and +/- zoom |
| Selection | selecting a feature announces its name via a live region; focus moves to the details panel only on the explicit "View details" action; closing returns focus to the marker or list item |
| URL state | `/explore?q=&category=&layers=&place=<publicFeatureId>`; only allowlisted keys (see `packages/public-ia`); selecting or clearing a place updates the URL without a full reload; a stale `place` shows "place not found" and clears itself |
| Attribution | always visible bottom-right, never hidden under panels or sheets; text comes from the basemap decision in `docs/architecture/gis-design.md` |
| WebGL / tile failure | the map area is replaced by the same searchable place list used as the permanent alternative, with a message that the map is unavailable; the list supports filters, selection and details identically; attribution of data sources remains in the footer |
| Empty / error | no results → message plus "Clear filters"; load failure → retry; stale snapshot is labelled with its date |
| Privacy | map layers contain only published public features; no interview positions or raw coordinates exist in any layer or URL |

Limitations: these are specifications, reviewed by me and not yet by a human designer or user testing; implementation is #72/#74.

## Mobile map bottom sheet (issue #16)

States: **peek** 112px (place name + Expand button), **half** 50vh, **full** (below the 56px header). All heights use `dvh`/safe-area insets (`env(safe-area-inset-bottom)`) so browser chrome and notches never cover content. Every state change is available as a visible button (Expand / Collapse / Close); dragging is an optional extra, never the only way.

| Concern | Specification |
|---|---|
| Floating controls | Search and Layers sit top of the map; zoom +/- sit right; attribution bottom-left of the map, above the sheet peek, never hidden by it |
| Soft keyboard | When a text field in the sheet is focused, the sheet is sized to the *visual* viewport (`visualViewport` API) and scrolls the field into view. The search field and its submit/clear actions stay above the keyboard; the sheet cannot be dragged below the field being edited. Search lives in the top bar, not inside the sheet, so an expanded sheet can never cover it |
| Orientation | On rotation the sheet keeps its logical state (peek/half/full); in landscape, "half" becomes a 360px side panel so the map keeps usable height |
| Keyboard / screen reader | Sheet is a labelled `region`; Expand/Collapse buttons have `aria-expanded`; Escape collapses to peek and returns focus to the selected marker or list item; the list alternative is reachable without the map |
| States | Loading skeleton with status text; empty ("No place selected" with a list of nearby places); error with Retry; offline/stale label |
| Reduced motion | State changes jump without animation |
| Limitation | Specification only. Behaviour on real iOS/Android keyboards is verified in #82/#117 on actual devices; not yet tested. |

## Place profile interface (issue #17)

Order (also the reading and tab order): title and category → source/verification status → summary → tabs **History**, **Media**, **Then & Now**, **Community findings**, **Sources** → related places. Tabs follow the WAI-ARIA tabs pattern (arrow keys, Home/End); on mobile they become an accordion with the same order and headings.

| Section | Present | Missing content |
|---|---|---|
| History | dated, sourced statements with evidence quality | "No verified history has been published yet." No fabricated dates |
| Media | gallery with date, credit, licence and alt text describing the evidence | "No approved photographs yet." No stock imagery |
| Then & Now | only when a verified pair exists (see #18) | section and tab omitted |
| Community findings | the safe cohort summary from #19 with n and caveat | "Not enough responses to show findings." (never zero) |
| Sources | every citation with licence and last-reviewed date; broken source flagged but citation retained | "No sources listed" blocks publication, so should not occur |

**Unpublished places:** a place that is not published returns the same safe 404 page as a place that does not exist, with no title, preview, metadata, thumbnail or search suggestion; server contract only returns `publicationState: "published"` features. Client code must not render drafts even if one were supplied.

## Community Insights dashboard (issue #19)

Implemented as a tested view model in `packages/insights-view` that the dashboard must use. Every chart is paired with a data table and a caption built by `captionFor()`, which throws unless **n, valid/missing/unsure counts, collection period and the sample note** are present.

| Situation | Display |
|---|---|
| Normal cohort | chart + table; caption "n = …, valid …, missing …, unsure …; denominator; counting rule; period; sample caveat" |
| Suppressed (small group) | "Hidden to protect privacy… not zero"; no number, no bar, no inference from totals |
| No data / absent / invalid count | "No data" (never 0) |
| Explicit zero from a ready cohort | "0" |
| Invalid payload (fails contract, leaks counts when suppressed, below k5, denominators mismatch) | "could not be validated"; not shown |
| Request failure | retry message, distinct from the above |

Allowed filters are only the fixed, reviewed cohorts and date windows the API supplies. There is no free-form query builder, and filter combinations that would reveal a suppressed group are not offered because the server returns them already suppressed. The sample note must say results come from a convenience sample and are not representative of all residents. Tests: 7 passing with synthetic fixtures. Limitation: the dashboard UI itself is #88/#91/#74 later; live data waits for Developer A's analytics API (#84, #92).

## Then & Now comparison (issue #18)

Logic is implemented and tested in `apps/web/src/thenNow.ts` (`viewPair`, `sliderKey`); the component (#68) must use it.

**Eligibility.** A pair is shown only if both dates are known, at least one source is cited and both images are available. Otherwise the whole comparison is hidden (no broken slider) and the profile shows nothing for it. An unknown or `unknown`-precision date is never formatted as a year or day: it reads "Date unknown", and a year stays "2021 (year)". A "2021 vs 2026" label therefore appears only when the record really has those dates.

**Viewpoint honesty.** The words "matched viewpoint" appear only when the record carries a matching note; otherwise the UI says the photographs are not documented as taken from the same viewpoint. Evidence quality and sources are shown beside each image.

**Layout and states.**
```text
[Before image: date (precision), credit, licence]   [After image: ...]
 slider handle: role="slider", aria-valuemin=0 max=100 now=50, label "Compare before and after"
 view toggle:  (o) Slider  ( ) Side by side  ( ) Text description
 sources: citation list   evidence quality: <value>   viewpoint: <matched note | not documented>
```
Keyboard alternative: the slider handle is focusable; arrows move 5, PageUp/PageDown 25, Home/End jump to the ends; the Side-by-side and Text description views need no pointer or dragging at all and are one control away. The text description is always generated ("Before: …. After: …. Evidence quality: …. Viewpoint …"). Reduced motion: no animated reveal. Loading shows a fixed-aspect skeleton; one image failing hides the pair and shows the text description with "An image is unavailable".

Tests: 6 unit tests (eligible pair, three unknown-date forms, missing source/media, no false same-angle claim, text alternative, keyboard model). Limitations: design plus tested logic only; the visual component is #68 and screen-reader behaviour needs human review (#114).

## Accessible field interview screens F01–F14 (issue #20)

Status: design specification plus an executable rules model (`packages/field-flow`, 22 tests). The field app itself is Developer A's. Written by Claude; no fluent-speaker, researcher or usability review has happened (see human actions). Wireframes for the main flow are in `docs/design/fieldwork-app.md`; the screen list is `docs/product/screen-inventory.md`.

**Global rules for every field screen.** One primary action per step, 44px minimum targets (56px for the main action), single column from 320px, readable in sunlight (AA tokens from #12 plus a high-contrast mode), no hover-only controls, visible focus, labels above inputs, error text beside the field and in a summary linked to the field, no timeouts that discard answers. A persistent header shows visit, connectivity (Online/Offline) and the save line from `statusLine`: "Not saved yet." / "Saved on this device. Not yet received by the server." / "Saved on this device. Offline: will send when connected." / "Saved on this device and received by the server." Language switch (English now; Gujarati only after fluent review) keeps all entered answers.

**Flow and states (what the model enforces).**

| Screen | Required states | Rule (tested in `field-flow`) |
|---|---|---|
| F01 Sign-in | signed out, wrong credentials, expired session, offline | no public registration; expired session keeps local drafts, asks to re-authenticate |
| F02 Dashboard | no visit, resume, offline-not-ready | shows last durable save time and queued count |
| F03 Visit | active, ending with unsynced records | cannot end with unexplained unsynced records |
| F04 Consent | unanswered, granted (with scopes), refused | no default selection; refusal ends the interview, discards participant content and GPS, and offers only "Start new interview"; scripts are versioned and the version is stored |
| F05 Participant | group chosen / missing | continue disabled with an explained reason until chosen; official-role claims stay "unverified" |
| F06 Interview position | not asked, captured (accuracy shown), denied, unavailable, manual | denied/unavailable are explicit outcomes and do not block the flow; accuracy above 50 m is flagged for recapture or review; manual pin requires a reason, keeps the raw fix and shows no accuracy; nothing is guessed |
| F07 Subject places | none, one, several | at least one place is required; each place is a separate topic; the interview position is never offered as a default subject; candidate places stay private until lead approval |
| F08 Questions | answered, unsure, refused, not asked | missing answers keep their reason and are never 0 or empty text; one answer per question per place; removing a place removes its answers |
| F09 Media | none, permission denied, partial upload | never blocks or destroys the interview; consent scope shown per item |
| F10 Review | clean, validation errors, write failed, saved offline, saved and synced | review shows "Where this interview was held (private)" and "Discussed: <place>" as two separate blocks; "saved" appears only after the device acknowledges a durable write; a failed write stays on review with data intact and the message "Not saved: <reason>. Your answers are still on screen; do not close the app." |
| F11 Queue | saved, sending, rejected, conflict, quota/lock | explicit retry; rejected items stay visible with the reason |
| F12 My submissions | by visit and status | an edit creates a new revision; no self-approval |
| F13 Candidate place | draft, submitted | private and unverified |
| F14 Site observation | draft, submitted | uses a dated rubric; never invents a respondent or consent record |

**Accessibility behaviour.** Step indicator is text ("Step 4 of 7: Subject place") plus a progress element; focus moves to the step heading on navigation; errors move focus to the summary; GPS capture announces "Position captured, accuracy 12 metres" via a polite live region; no colour-only status (icon plus words); support 200% text and portrait/landscape; reduced motion honoured.

**Consent wording.** Final consent scripts, scope names and the Gujarati text belong to the research lead and ethics approval. This design deliberately contains no consent text; the model only requires a script version and language to be recorded.

**Verification.** `pnpm --filter @makarba/field-flow test`: 22 passed, covering refusal discarding data, no capture before consent, interview position versus subject separation, GPS denied/unavailable/poor/manual/invalid, missing answers kept as missing, failed writes, offline save versus synced receipt, and saved records being immutable.

**Limits and handoff.** Not tested on a phone, with a screen reader or with researchers; time-to-complete is unmeasured (pilot, #62/#118). Developer A must make the real app pass equivalent tests (handoff note: treat `packages/field-flow` as the rules oracle). Role behaviour (#6) is unverified against the real permission system.
