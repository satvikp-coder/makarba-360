# Two-person coordination and PR workflow

Use developer-issue-allocation.json as the authoritative ownership/dependency record. CSV, guides, issue sections and summaries are generated by `allocate_workstreams.py render`; do not independently change their estimates or ownership. The immutable allocation-baseline.json makes changes reversible and preserves every original issue body, assignment, milestone and linked event. It is an audit snapshot, not live readiness.

1. Fetch current main, inspect issue and hard-prerequisite evidence, then create `dev-a/issue-N-slug` or `dev-b/issue-N-slug`. B can use a fork while collaboration is pending; this does not make B assignable or grant raw data access.
2. One focused issue or tightly related small scope per PR. State contract version, files touched, expected output and handoff partner. No real participant data or credentials in fixtures, screenshots or logs.
3. Provider changes begin with schema/examples/fixture version and consumer impact, before service/UI work. Both developers approve breaking interfaces through PR discussion; a domain producer cannot silently change another developer's contract. Additive optional fields are reviewed and tested; removal/semantic changes require a new major contract and migration window.
4. Run the applicable tests, including `python scripts/verify_planning.py --local`, `python scripts/verify_allocation.py --local`, and `python scripts/check_public_contracts.py --fixtures` for planning/contract changes. Product changes later run their actual unit/API/spatial/browser/permission/fault suites. Passing the planning tests is not product acceptance.
5. Open a meaningful PR referencing the issue, inspect available CI and cross-review shared schema, auth, publication, privacy and migration boundaries. Preserve PR links and failure evidence. Do not merge failed checks or push directly to protected main.
6. Merge only when required checks and permissions allow, verify the actual merged commit and relevant runtime evidence, then close the issue. Mock-backed component acceptance must say so; integration issues and real-data release gates remain open until actually verified.

Reviewer unavailable: continue a ready independent task or draft the implementation. Do not bypass protected checks or mandatory review. An isolated low-risk documentation/copy change without interface/privacy/schema impact may receive owner-reviewed merge after recorded self-check and passing CI where repository policy permits. Shared contracts, consent, raw-data access, publication, migrations, sync conflicts and production deployment wait for peer review; no automatic self-approval. A verified account can comment/review a public PR even while membership is pending, but that is not assumed to satisfy a protected required approval.

Conflicts: fetch/rebase or merge current main, inspect both versions and ask the owning developer in the PR before changing semantics. Preserve both contributors' intended behavior and rerun impacted tests. No force-pushing shared branches, overwriting applied migrations or deleting valid issues to make balance look equal. No external messages are sent by this planning run.

Incremental integration receipts record issue/provider/consumer, contract hash, synthetic fixture version, commands and expected/actual results, current revision/commit, privacy review and remaining limitations.
