### Summary
Every private route evaluates role, study and record ownership.

### Why this is needed
Implement role and study authorization enables the authentication, privacy and data security workstream while preserving the researcher-led evidence chain. Without this deliverable: researcher cannot read another study or grant admin role is not established or verified.

### User story
As a authorised team member, I need this reviewed capability so that every private route evaluates role, study and record ownership.

### Scope
- Every private route evaluates role, study and record ownership.
- Implement/review the associated contract and observable error states described in `docs/architecture/privacy-security.md`.
- Capture evidence for the negative case: Researcher cannot read another study or grant admin role.

### Out of scope
Other backlog issue deliverables, unrelated refactors, real data committed to Git, and unapproved paid-provider activation. Planning/design/research issues produce reviewed artifacts rather than application code; implementation issues build only the stated capability.

### Technical approach
Central authorization service with deny-by-default capabilities. Follow `docs/architecture/privacy-security.md`, `docs/architecture/data-model.md` and the relevant ADR. Keep migrations, runtime validation and UI contracts consistent where this task changes them. Document a justified alternative before changing architecture.

### Data and privacy considerations
Deny by default and minimize retained personal data; current consent and scoped study grants are authoritative. Do not copy sensitive inputs into issue comments, test artifacts or operational logs.
